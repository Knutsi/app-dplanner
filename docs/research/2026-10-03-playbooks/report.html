Playbooks: a chain of agents around one step

Can a plan step run a playbook, where Claude implements, Codex reviews the worktree, the verdict travels back and a gate decides finish? This report weighs the evidence, settles the shape, compares two ways to drive it, and works through what fails. The failures were probed for real against claude, codex and opencode, at no cost. Every prototype output below is generated by the spike in spike/.

1The answers

In short

A playbook is a list of gates around the step's own work, driven by DPlanner's engine. Its stages are kept in the rounds ledger the step already has. A second agent earns its cost through the tests it runs and the fresh context it brings, not through being a different model. The hard part is failure handling and what people see, not the happy path.

Better than self-review?

Partly, and mostly because of the tests

Tests and execution give most of the gain. A fresh context adds a little. A different vendor helps only if it is at least as strong. An agent spawning a reviewer subagent with its own context is the worst option measured.

2Self-review or a second agent?

In short
  • An external signal does most of the work. Self-correction with nothing outside to check against mostly fails: one study fixed 7.6% of wrong answers and broke 8.8% of right ones.
  • A fresh context is a small, real gain. A subagent that carries the implementer's context is the worst of four conditions tested.
  • A different model helps only when its feedback is better. A weaker cross-vendor reviewer made code worse (13 regressions for 3 fixes).
  • Debate is mostly cost. Majority voting explains most of what it gains.

No study measures fresh context, a different model and an external signal against each other in one experiment, so this is pieced together from separate studies. Full citations are in evidence.md.

What it means for a playbook

  • The criteria gate (tests) comes first and decides. DPlanner records it from exit codes.
  • The reviewer is fresh, read-only, can run the tests, and never sees the implementer's justification.
  • Findings carry evidence and pass a falsification step. The implementer fixes or declines with a reason, never argues back in a loop.
  • The cheapest preset is the control: the same agent, a fresh session, a checklist and the tests. A careful preset has to beat it on our own steps before it is the default.

3The shape: a list, not a graph

In short
  • The plan step stays one card. It is the work stage: the slot the template wraps.
  • Every other stage is a gate, and changes sends the work back. So the stage graph is a star, written as a list. The one escape hatch is on_changes.
  • The gates: criteria (exit codes, run by DPlanner), checklist (yes/no with evidence), judgement (open review by lenses). A person gate comes last.
  • Roles are portable (harness + model) and live with the playbook. Profiles stay per machine; a role maps to the first profile for its harness, as _profile_for already does.
  • Presets: Solo ($2), Review loop ($4), Careful change ($12). Solo per step, Careful on branch landings. Edited through a form, kept as a file.

The 99% case you described, A ⇄ B → done, is the Review loop playbook in the Prototypes section. check() accepts it, with one warning: no criteria gate: nothing runs the tests, so every gate is opinion. That warning is the evidence talking, so the shipped preset puts a tests gate before the review. It costs no tokens.

When a pass stands. A criteria pass counts only for the commit it ran on. An agent's or a person's pass stands once given, even after another gate's fix. Re-reviewing everything after every fix doubles the cost. The careful/person-sends-back scenario shows it: the person sends the work back, the tests re-run on the new commit, and the review's pass stands.

rounds is how many times a gate may see the work. Changes on the last round escalates to a person; there is no extra round (review-loop/cap).

A fix resumes the implementer while it is warm (inside the cache TTL, under ~100k context) and goes fresh otherwise. In careful/person-sends-back the person took 50 minutes, so the fix went fresh.

4Who drives it

In short

One definition, two drivers. DPlanner's engine runs a pure, level-triggered due(playbook, ledger, facts). A lead agent gets the same playbook as its briefing (lead_briefing()). The evidence favours the engine for a step: a fixed review pipeline beat an agentic one 2.2× at 5–15× fewer tokens, and multi-agent setups did 39–70% worse on sequential tasks. Either way, DPlanner records the facts (criteria results, which run holds the stage, the SHA judged, spend), so a lead agent can only propose.

A third form: compile the playbook into a Claude Code workflow script (deterministic and resumable). Its own docs say "no mid-run user input", it ties every stage to Claude Code, and DPlanner's ledger would become a copy. Useful as a reference design, not as a driver.

The scenario lead/lies-about-tests shows why the facts are DPlanner's. The lead reports the tests green. DPlanner refuses that report, because a criteria gate is recorded from exit codes, and its own run says red.

5What makes it pleasant

In short

The mechanics are the easy half. 6The factory floor

In short
  • A step is claimed whole; a person's stage is assigned to a role or a named person, and answering it does not take the step from the worker.
  • Review time is the bottleneck: teams heavy on AI merged +98% PRs, took +91% review time, and saw no gain in delivery (Faros). So there is one person gate per branch landing, and it leads with evidence.
  • People own the work; agents are delegates. Take over fences the worker's run. Hand back sets the outcome, and the next tick carries on.

A quota park is capacity a plan must not assume. Resource planning counts a worker's concurrent runs and its accounts' quota windows next to people's hours.

7Failures and edge cases

In short
  • The ledger is the truth; processes are disposable. Every ending is classified, and only a real verdict spends a round. The simulation asserts this in every scenario, along with "never two runs live at once".
  • The probes found four things the plan did not know:
    • no CLI times out a hung API;
    • opencode loops forever on a malformed reply (3,698 requests in 330 s) while still emitting events, so a stall detector is blind to it;
    • Claude retries a dead login for 3 minutes, and Codex gives up on a 429 at once without honouring retry-after;
    • Claude's error result says "subtype":"success", and only is_error tells the truth.
  • A subscription expiring mid-run trips a circuit breaker on that account. Every stage on it waits for a login interrupt, the others go on, and the dead agent's worktree is resumed after login (fail/auth).
retrytransient: crash, hang, 5xx, malformed output. Backoff 30 s → 2 min → 10 min; three in a row → a person.
parka quota or rate limit with a reset time. The account waits; the person is told.
persona login gone, billing, a question, a retired model. A typed interrupt; other accounts go on.
abandonwill not improve by waiting: a runaway loop, a broken config. Stop, then a person.
changesa real verdict from a gate. The only class that spends a round.

8Prototypes

In short
  • playbook.py: the loader, check(), the pure due() engine, fencing at intake (accept()), the ring label, the lead briefing and the diagrams. About 600 lines; mypy-strict and ruff clean.
  • simulate.py: 22 scripted scenarios through the engine, rendered as the three chatter layers plus the inbox, refusals, cost and invariants. All invariants hold. Writing it caught two bugs in the engine: a fix launched twice, and a budget that blocked a person's approval.
  • classify.py + probes/: the failure classifier, built and tested on real CLI output.
  • Not run: the live experiment with real agents. It spends subscription quota and waits for your go-ahead (question 10).

- Report every verdict with `dplanner review post|approve --run <your run id>`. A verdict
  from a run that no longer holds the stage is refused.
- Criteria gates are run and recorded by DPlanner (`dplanner playbook check-gate <stage>`);
  your report of a test result is not accepted as one.
- Budget: $12 for the whole step. Check `dplanner playbook spend` before each
  launch; at the limit, stop and run `dplanner review escalate`.
- An agent that fails to start, times out or hits a quota is not a round. Never count it.

Roles (start each as its own headless process; never reuse a reviewer's session):
- implementer: `claude` (opus)
- reviewer: `codex`, fresh session
- security: `codex`, fresh session

Stages, in order:
1. work — the implementer does the step, then reports ready.
2. tests — DPlanner runs: uv run pytest -q; uv run ruff check; uv run mypy. Any failure is changes.
3. review — reviewer reviews (correctness, architecture), up to 2 rounds.
4. security — security reviews (security), up to 1 round. Only when the diff touches src/*/auth/*, src/*/net/*, *.lock.
5. approve — wait for a person's approval. Do nothing until it arrives.

When a gate asks for changes, send its findings back to the implementer (resume its session
if it ended under an hour ago, else start it fresh with the findings), then run that gate
again. Earlier criteria gates run again on the new commit; earlier agent passes stand.
When a gate's rounds are used up and it still asks for changes, escalate. Never approve
on a gate's behalf, and never approve for the person.

9Questions for you

In short

Twelve decisions, each with a recommendation, so a one-word answer per line is enough. The ones that unblock building are 1 (list, not graph), 2 (the file format), 5 (engine first) and 10 (run the live experiment).

  1. A list of gates (a star around the work), or a free stage graph?
    recommendThe list, with on_changes as the one escape hatch
    Every case we could name fits it. A graph editor is the "squeezed from both directions" builder. Add a graph only when a real playbook needs one.
  2. The file format for a playbook definition?
    recommendTOML in <plan repo>/playbooks/, edited through a form
    A person authors it and wants comments in it; the standard library reads it. It is the first hand-authored config in a JSON codebase, so FORMAT.md needs a line on why. The alternative is JSON written only by the form.
  3. Where do playbooks live?
    recommendBuilt-in presets, shadowed by the plan repo's playbooks/, and later the system level (v2 idea 1)
    Versioned with the plan, shared by everyone who opens it. Project wins over personal, as Factory droids and Claude workflows do.
  4. Does an agent's pass stand after another gate's fix?
    recommendYes, unless the fix touches a file the earlier gate flagged
    Re-reviewing after every fix doubles the cost. The exception catches the case that matters.
  5. Build the lead-agent driver?
    recommendEngine first; the lead later, as an experiment on the same ledger
    The evidence favours the engine. The lead is cheap to add once the engine enforces criteria, fencing and budget, and only running both measures the claim.
  6. Must a careful playbook have acceptance criteria before it starts?
    recommend**Yes for Careful change; offered for the others**
    Without criteria every gate is opinion, and opinion over-flags. A drafted validation contract a person accepts in one click is the Factory pattern.
  7. The default playbook for a new project?
    recommend***Solo* per step, Careful change on branch landings**
    The person gate goes where it is paid for once (floor.md).
  8. Who answers a person gate?
    recommendA role, defaulting to the step's owner
    Named people for small teams, roles for the floor, with the same field.
  9. **When only one vendor's CLI is installed, should Review loop fall back to a same-vendor fresh review, or refuse?**
    recommendFall back, and say so on the ring
    It is still the "fresh context + tests" control. Refusing teaches nothing.
  10. Run the live experiment (claude -p implements, codex exec --sandbox read-only reviews, one fix round, on a toy repo in the scratchpad)?
    recommendYes, once. It costs roughly $1–3 of subscription usage.
    It turns the simulation's assumed tokens and minutes into measured ones, and records a real stream for the transcript viewer. It was not run tonight, because it spends quota and needed your go-ahead.
  11. Add a harness classify() and stall threshold to AgentHarness?
    recommendYes, with the probe fixtures as its tests
    The probes showed each CLI fails differently (Claude's 3-minute 401 retries, opencode's endless loop). A shared classifier would need to know every CLI's quirks; one per harness keeps each quirk with its CLI.
  12. Keep the probe runner as a maintained script (scripts/probe_harnesses.py) to re-run when a CLI updates?
    recommendYes
    CLI error behaviour changes monthly, and a classifier built on last month's shapes fails silently.
