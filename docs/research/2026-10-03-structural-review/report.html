Fix what's broken, then prove the shape on one workflow

This is where the three passes ended up: the review, Codex's second opinion, and my response, plus Knut's decisions of 4 October. The rest of the page is the reasoning: §12 reconciles the reviews and §14 records the decisions.

  1. Correctness first: small PRs, no design decisions.
    • write_atomic gets a unique temporary file.
    • set_checkout stops hiding the other writer's membership change.
    • CompositeCommand becomes all-or-nothing.
    • An unknown status is never due.
    • touch stops bringing back ended claims.
    • Undo refuses to overwrite a value another writer changed.

    Done when each of Codex's six probes is a regression test that passes.

  2. Pilot one complete workflow, set status, end to end.
    • planning/status.py owns the vocabulary as an Enum, with Unknown as its own type, plus the readiness rules. There's no state machine; out-of-order recording stays.
    • step_status/workflows.py: set_status(...) -> Change is called by both the window and dplanner status set, underneath the context system, which stays as it is. Under the director rule, the window gains the claim release it lacks today.
    • The first architecture tests:
      • planning/ imports only core and domain.
      • One module reaches another only through aspect.py or workflows.py.
      • The module graph is acyclic.

    Done when the GUI and CLI give the same outcome for every status change, the literal-"done" comparisons are type errors, and a status change touches measurably fewer places than today.

After the pilot, extend the same pattern: the kind facts, then the root's clusters, then launch as an external effect before the daemon. Multiplayer is now a ladder (§14): git stays the only authority, and an advisory coordination service broadcasts presence, area claims and pushes. Before the second rung, two things are needed: project.dproj must stop colliding on step adds, and step numbers need a small design of their own.

Decided on 4 October:
  1. Multiplayer coordinates; git is the authority. A service linked from the plan repo broadcasts presence, area claims and pushes. It holds no plan data.
  2. The director has authority over the worker. When the window sets a step done, the agent's claim ends.
  3. workflows.py sits under the context system, which stays. It was renamed from actions.py, because "action" already means ActionSpec.
Still open: the step-number design for rung 2, and whether workflows.py goes into CLAUDE.md after the pilot.

Where DPlanner is starting to crack

An entropy and structural review before the v2 work: playbooks, a headless daemon, and a multiplayer server. It covers what has held, which patterns are emerging, which seams will give under more writers, and what could replace the composition root.

1Verdict

In short

The layering rules have held: test_architecture and test_rules pass (17 tests, run for this review), modules really don't import each other, and the model knows nothing about aspects. The pressure those rules hold back has gone into the composition root, and the persistence layer is still shaped for one writer at a time. Keep the root and narrow its job: move the planning ontology (status, estimates, step kinds, the review workflow) into a new headless planning/ tier, and let what remains cross modules through headless imports. Before the daemon, fix the coordination seams.

What has held

  • The dependency direction is enforced, not just hoped for. core → domain → cli → framework → modules → root holds across 126k lines, and the test fails on a violation.
  • The graph model has no aspect knowledge. model.py, store.py and commands.py never read a module id, and an unknown aspect round-trips untouched.
  • The headless CLI is real. A verb and a menu action build the same command, and the CLI starts without Qt.
  • The engineering habits stuck: blocking work goes through TaskRunner (23 call sites, none bypass it), rebuilds go through Debounced (26), and derived facts are never stored.

What is cracking

  1. The composition root has turned into a feature module. About 1,900 of its 4,923 lines are business logic that has no owner, and 36% of all commits touch it.
  2. The step ontology has no owner. "What kind of step is this" is ranked separately in about six places, and "done" means three different things.
  3. Seven package names no longer say what the package holds, and nothing sets a convention for which file holds a tab.
  4. Persistence assumes one writer. Commands aren't operations, every concurrent step add conflicts, numbers are minted locally, claims are machine-local, and two real two-writer bugs exist today.

Recommendation, in three lines

Keep the root, as wiring

It is still the right pattern. Take away the second job it picked up: being the only place allowed to know two modules.

A planning tier, then imports

The step ontology moves into a new planning/ tier between the graph and the features (§5). What crosses modules after that goes through headless imports along a graph a test keeps acyclic.

Coordination before the daemon

Fix the two bugs, lock check-and-write, give claims a headless lease, and move "what is due" out of Qt. Turn commands into operations before the server.

2Findings

In short

(a) Entropy: ghost packages, an LLM stack with no caller, callback indirection that nothing substitutes, and docs that have become diaries. (b) Emerging patterns: the root as a feature home, an ontology written six times, names that no longer say what a package holds, and features leaking into framework/. (c) Cracking seams: two verified two-writer bugs, commands that aren't operations, and conflicts that are coarse.

(a) Entropy and over-engineering

  • Ten ghost packages hygiene

    agent_skill, llm_anthropic, llm_openai, product, project_dashboard, project_repo, step_feature, step_handoff, step_release and workspaces hold only __pycache__. Git can't see them, but anyone opening modules/ for the first time does.

  • An LLM stack with no consumer speculative

    LLMService.complete() (framework/llm_service.py:126) has no caller outside its tests. framework/llm.py, key_dialog.py, modules/llm, the provider halves of anthropic and openai, and Debug's LLM Calls tab are all waiting for v2 step 7. Keep it, but move it out of framework/, where it is a divergence from app-framework that serves nothing.

  • Callback indirection that nothing substitutes over-engineering

    50 *Deps classes carry 480 fields; StepAgentInstructionDeps alone has 37. One function, _step_key, is handed to about 11 modules as key_of= or step_key=. About ten root helpers only rename an aspect reader:

    src/dplanner/modules/__init__.py:3109one of ten

    """Whether a step is a wait — the wait aspect's answer, for modules that may not ask it."""
    from dplanner.modules.step_wait.aspect import is_wait

    return is_wait(step)

    The docstring says it plainly: "for modules that may not ask it." The rule forbids the import, so the root does the import for them and passes the result down a callback. The dependency is still there. It just doesn't show up in the module that has it.

  • Docs that have become diaries entropy

    ARCHITECTURE.md has 8,843 lines in 75 sections, in the order they were written, with 37 "used to", 26 "no longer" and 20 "retired". NOTES-FOR-APPFRAME.md has 4,932 lines, and §§7–75 are titled "From the X pass…", so it can't answer "what differs from upstream in framework/x.py?". CLAUDE.md's Mechanical facts (about 140 lines) are rules for particular areas, and its own policy sends those to .claude/rules/.

  • HEADLESS_FILES matches a bare filename anywhere in the tree fragile rule

    The list in tests/test_architecture.py:54 has 59 names. Two of them match no file (categories.py, catalogue.py), and any future schedule.py or edits.py in any package would be forced headless.

  • Small duplications hygiene

    There are three git runners in core/storage, two gh wrappers, and three detached-process spawns. Only the launcher's spawn sets the Windows flags. spawn_instance (library/module.py:45, which New Window uses) relies on start_new_session, and that is POSIX-only.

  • Names that no longer say what a package holds pattern

    The canvas is called project_editor. projects holds the step CLI noun. progression holds the Step statuses tab. step_order holds Expenditure. step_agent_instruction holds Run Agent. step_agent_run holds a second module id, agent_usage. The details are in §7.

  • No convention for which file is the tab pattern

    The tab is in activity.py in 7 modules and inside module.py in 3. view.py means five different things across 10 modules: a tab, a table, a modal, a status-bar widget, shared widgets.

  • framework/ is collecting features divergence

    llm*, key_dialog, dictation*, recording and motion/ are features, and they sit in framework/. About 12 framework files import domain. Each of these is a divergence that a later upstream pass to app-framework will run into.

  • domain/ is collecting aspect vocabulary pattern

    progression.py:71 owns the status words, shelf.py reserves a module_data key, and schedule.py mixes formatting (format_date, axis_ticks) with simulation.

  • Off-stack mutations are spreading pattern

    Only two kinds of change are documented as bypassing the undo stack. Even so, .redo(library) is called directly at step_status/aspect.py:154,173, step_agent_run/aspect.py:105,116 and step_review/rounds.py:205. projects/cli.py:765,1030,1052 call membership without an origin.

  • Tests are flat entropy

    tests/modules/ has 110 files, and 48 aren't named after their package (test_canvas_*, test_time_*…). That is why the rules files' paths: list test globs by hand, and why test_agent_run.py mostly tests step_agent_instruction.

(c) Seams that are cracking

These are summarised here; §8 has the detail.

  • write_atomic shares one temporary file between processes bug · verified

    src/dplanner/core/fsio.py:54
    tmp = path.with_name(f".{path.name}.tmp")
tmp.write_text(text, encoding="utf-8", newline="\n")
tmp.replace(path)

    The GUI and the CLI both write the library file and the at-work claims. Two writers share .library.tmp, so one can rename the other's half-written file into place, or fail with FileNotFoundError.

  • set_checkout hides the other writer's membership change bug · verified

    src/dplanner/domain/store.py:588
    file = read_library_file(self.library_path, strict=True)
write_library_file(self.library_path, file.projects, self._checkouts, file.archived)
self._remember_library_stamp()
self.checkout_changed.emit(key)

    The other writer's project rows survive the write, but the re-stamp records the file as already seen. So this window never adopts their change, and its next membership flush writes its own model's list and drops their project. Their checkout keys are replaced by this window's too.

  • Commands are not operations seam

    A command holds live Node objects, captures before lazily, uses an object() sentinel as its origin, and carries no id, author or base version. Undo restores values it captured, which silently overwrites another writer's later change. See §8.

  • Conflicts are coarse, and the check is separate from the write seam

    A step's meta holds its title, edges and number. project.dproj holds the children order and last_number, so any two writers who each add a step conflict. Step numbers are minted locally, so both of them mint S8.

  • Coordination is machine-local and needs Qt seam

    Claims carry no agent identity, and touch can bring an ended claim back. The launch lock is a QLockFile. due_here is a closure inside the GUI's default_modules().

  • Loading writes, and slots swallow exceptions seam

    load() writes migrations (store.py:344), so two builds that disagree on the format migrate the plan under each other. Signal.emit logs a failing slot and carries on (core/signals.py:61-66), while the store's conflict bookkeeping depends on those slots.

3How the composition root got here

In short

"Modules never import each other" is enforced and it works. But some knowledge can't be avoided: the briefing has to know a step's PR, and the card has to know whether a step is a milestone. That knowledge had nowhere to live except the one file allowed to import everything. Without anyone deciding it, the root took a second job, and every feature that touches two modules now edits it.

4Alternatives, compared

In short

Below are seven approaches, each shown on the same two pieces of code. My recommendation is the hybrid (3): a module may import another module's headless files, along an import graph a test keeps acyclic; questions many modules answer become extension points on AspectSpec (as phrase already is); services stay on Deps. Splitting the root (1) is a cheap first step whichever you choose. The event bus (4) and the service locator (5) both make things worse. Bounded contexts (6) is where the hybrid's graph leads later, not a place to start. §5 refines the hybrid: most of what it would import is the planning ontology, and that is better served by a tier of its own.

The running example

Every approach below is written out on the same two questions, because they are the two shapes of cross-module knowledge:

  1. A question many modules answer: the step's key letter. _step_key asks five aspects in a fixed order and is handed to about 11 modules.
  2. A question between one pair of modules: the briefing reads a step's PR. _source_line (root:2308) imports github.aspect.read to tell an agent which branch and PR its source work is on.

2 · Extension points only

sketch · domain/aspects.py
@dataclass(frozen=True)
class Kind:
    rank: int          # lower wins: the coarser claim
    letter: str        # the key's letter, "M"
    word: str          # "milestone"
    icon: str = ""     # the medallion, "tag"

@dataclass(frozen=True)
class AspectSpec:
    ...
    kind: Callable[[Step], Kind | None] | None = None

def classify(specs: Sequence[AspectSpec], step: Step) -> Kind | None:
    claims = [k for spec in specs if spec.kind and (k := spec.kind(step))]
    return min(claims, key=lambda k: k.rank, default=None)

def key_of(specs: Sequence[AspectSpec], step: Step) -> str:
    """"M12": the kind's letter and the number the project dealt."""
    if not step.number:
        return ""
    kind = classify(specs, step)
    return f"{kind.letter if kind else 'S'}{step.number}"

3 · Hybrid: headless imports along an acyclic graph, plus extension points

recommended

Each kind of cross-module knowledge goes through exactly one channel:

A fact another module owns

Import its headless files (aspect.py, prompt.py, rounds.py…). Never its module.py or anything that uses Qt.

The briefing reads the PR. Review reads the status.

A question many modules answer

An extension point: a field on AspectSpec, or a report.py-style file.

The key letter, the medallions, briefing sections.

A live service

A callback or Protocol on Deps, as today.

The store, window capabilities, TaskRunner, follow_project.

The graph that test would see: simulated from today's root

I parsed every function in the root, recorded which modules it imports, assigned each cluster to the owner it should have, and ran a cycle check. The first attempt found two cycles, and each one pointed at code in the wrong place:

  • branches → step_agent_instruction → step_status → branches. If the briefing goes into step_agent_instruction, it imports branches, which imports the launcher back. Fix: the briefing gets its own package, agent_briefing.

With both fixes the graph has 31 edges and no cycles. This is the main argument for the hybrid: when you try to place code, the cycle check tells you where it belongs, which the root has never been able to do.

5A planning tier

In short

Suppose the core aspects move into a new tier between the graph and the features: status, estimates, step kinds, the review workflow. It's a good move if the tier holds the planning ontology and nothing else. In simulation it absorbs 23 of the 62 root helpers that read other modules, and it gives v2's server and daemon something to import that isn't a feature. It's a poor move if it becomes "the important aspects", because then it turns into a second composition root. The guard is an admission test. Everything else stays where it is: the execution family (briefing, launch, PR refs) and the knowledge family (spec, docs, tests) are features working with each other, not ontology.

Why it is good for long-term complexity

  • Dependencies point toward stability. Everything reads status and kind, so they belong low. Today they sit high and get pushed down through callbacks, which is where the 480 Deps fields and the six copies of the ranking come from.
  • One concept, one place. The words, the storage format and the rules of status end up in one module.
  • New features get cheaper. A long-tail feature imports planning/ downward and needs no root callbacks. A feature that changes the ontology (playbook stages, claims) has to touch planning/ deliberately, and that friction is right for something everything reads.
  • v2 becomes possible. A multiplayer server can import domain and planning and nothing else. That lets it validate status transitions, mint step numbers and merge the core aspects with real rules, while long-tail aspects stay opaque blobs merged per entry. Without the tier, the server would either load feature modules or be unable to enforce anything. The daemon's question, "what is due?", is a planning question.
  • It shrinks the hybrid. Once the most-read aspects move below the modules, most of the cross-module edges that remain are inside one family. That suggests the long-term structure: families as bounded contexts, found from the data rather than drawn up front (§4, approach 6).

Where it goes wrong, and the guards

  • Kernel creep biggest risk

    domain/ already shows it: agents.py, dictation.py, ledger.py and document_folder.py are plugin contracts sitting next to the graph.

    Admission test: an aspect belongs in planning/ only if a headless server or daemon must interpret it to order, claim, validate or merge, without loading any feature. By that test, description, ticket, notes, docs, spec, testing, usage and GitHub sync stay out.

  • Work refs are borderline decide later

    Branch and PR refs are read by 6 helpers, and claims and landings need them. A vendor-neutral "where this step's work lives" (branch, PR number, state) is execution ontology and could belong in planning/. The github module would then be the provider that fills it in, off the undo stack as it does today. Decide when the daemon lands.

  • Changes split across tiers a tax

    For about 11 features, the data contract lives in planning/ and the UI in modules/<name>, so a change to estimates touches two packages. That's acceptable for the most stable data and for nothing else, which is why the long tail stays in single packages.

  • Status is still moving timing

    Playbooks will add stage states. Move status down as an explicit state machine with allowed transitions, not as today's bag of words. A server and a daemon need the transitions anyway.

  • Presentation creeping in discipline

    The tier says "milestone" and "M". Glyphs, tones and colours stay in the canvas and the theme, keyed by the kind word.

  • Losing real substitution keep one seam

    The simulator does feed the schedule alternative readers. Keep function parameters where a second implementation exists, with the planning readers as defaults, and drop them everywhere else.

  • Naming

    Not "core", because core/ already exists. planning/ says what it holds. The layer test gains one rule: domain/ never imports planning/, and planning/ imports no Qt and no module.

What it changes in the recommendation

It doesn't replace the hybrid; it takes over most of its work. The tier holds the ontology (the 23 helpers), and what is left goes through headless imports, mostly within one family. Wave 2 becomes "create planning/ with kinds and status" instead of "add AspectSpec.kind". That's a better pilot, because it tests the tier and the ontology together.

The decision this asks for: declaring the planning model fixed. In practice, status, estimates, kinds and the review workflow become DPlanner's own concepts, no longer something any module could replace. The measurements say the code already treats them that way. The tier would make it official.

Origins are object() sentinels (UNDO_ORIGIN, OUTSIDE_ORIGIN), so they can't be serialised. Builders such as rewire_command produce whole-list replacements read from the live library, against a base nobody records. Undo restores captured values. The undo service already drops history when the document refuses a command (framework/undo.py:162-171), but only a missing node or a text mismatch counts as a refusal. A value another writer changed is just overwritten.

Where the proposed remedies need qualification

  • Give planning concepts owners agree, with limits

    A planning/ tier is a good home for status, readiness, estimates and scope. It needs ownership and versioned contracts, without declaring the model permanently fixed. One kind ranking cannot replace every policy: keys choose identity, medallions show several aspects, primary glyphs identify workers, body colours incorporate completion, and scope defines traversal boundaries. Centralise shared facts while preserving those questions (modules/__init__.py:2975–3107, _scope_kinds).

    A restrictive status state machine is a product change. domain/progression.py deliberately honours manually recorded, out-of-order completion. Preserve that when extracting the rules; require an explicit compatibility decision before an unknown state can authorise execution.

  • Headless and acyclic is not a public API missing guard

    An acyclic graph can still couple every feature to other features' internal schemas and helpers. Permit imports through small, explicit headless APIs, and enforce that boundary. Pure queries can be ordinary functions; storage, clocks, execution and external services still benefit from injected dependencies, even with one production implementation.

    Callback counts, line counts and template divergences are warning signals, not proof. Off-stack writes also need context: record_started and record_merged deliberately record external facts undo should not reverse (step_status/aspect.py:140–174).

  • Complete actions need one owner additional alternative

    Keep a modular monolith with explicit application actions: approve a review, record completion, link steps. GUI, CLI, daemon and server call the same headless action. It coordinates validation, related changes, persistence and notifications of accepted changes. Generic field commands remain building blocks, and UI undo remains a separate concern.

    The status CLI already combines actor-specific rules, decision notes, claim release and the write (step_status/cli.py:67). Sharing SetModuleDataCommand alone does not share that behaviour. This is a useful middle ground: no generic message bus, microservices or interface around every pure function is needed.

Decide what multiplayer owns

The meeting notes describe presence, claims and messaging alongside Git. Parts of this review assume a server that accepts and merges plan edits. Both are possible, with different costs and guarantees.

Intended capabilitySuggested architecture
Presence and coordinated workers; Git carries plan changesA coordination service, with explicit limits on concurrent editing.
Live shared plan editingOne authoritative mutation service per project, transactional acceptance and subscriptions.
Independent offline editing that later mergesExplicit merge semantics for each data type; substantially more design work.

For live shared editing, prefer the second option initially. Serialising accepted changes per project simplifies graph validation and numbering; this is a logical authority boundary, not one deployed process per project. The current core/storage/provider.py requires a local working directory, so a remote mutation service needs a boundary above file operations.

Gaps in the operation and coordination sketches

  • Per-entry versions do not protect graph-wide invariants. Two writers can independently add opposite dependency edges on different steps. Neither entry conflicts; the combined graph has a cycle. Validate the resulting graph inside the acceptance transaction.
  • Composite commands are not transactions. Multi-entry changes and their undo need all-or-nothing acceptance. Add transaction grouping to the operation sketch. Compare versions for undo: matching values alone cannot establish that nobody edited an entry in between.
  • A post-write check cannot guarantee detection of an overwritten Git update. App-controlled checkout/pull and writes need coordinated ownership at repository scope. Arbitrary external writes need a recovery policy; a per-project lock also leaves the separate library file uncovered.
  • Presence and exclusive ownership are different contracts. Execution needs atomic acquisition, owner-checked renewal and rejection of obsolete owners when accepting protected writes. An expiry and owner id alone are insufficient. The etcd locking contract illustrates checking ownership within the write transaction; it is a design reference, not a recommendation to add etcd.
  • A launch is an external effect. The current launcher spawns before due.claim() (step_agent_instruction/module.py:800), and the pass flushes later. A crash between those steps needs reconciliation, not a blind retry. Durable run intent, run identity and recovery belong in the execution boundary; a plan transaction cannot itself atomically start an external process.
  • Step numbers are public references. Branches, briefings and people name them. Collision repair by lint is not harmless: use authoritative allocation, or deliberately design an offline allocation scheme preserving stable references.

Suggested order and proof of improvement

  1. Fix the reproduced persistence bugs and unsafe unknown-status interpretation, with regression tests. Protect foreign edits from stale undo.
  2. Pilot one complete workflow: planning rules with a clear home, a headless application action and the same outcome through GUI and CLI. Exercise competing writers and failure partway through a change.
  3. Settle transaction and multiplayer authority boundaries before expanding cross-module imports. Distinguish durable plan data, execution ownership and local UI state.
  4. Move and rename packages as their responsibilities become clear. Preserve on-disk ids. Shorten the current architecture guide and keep dated decisions separately.

A transactional store is a credible alternative to growing a custom file transaction system. SQLite supplies atomic commit and recovery; whether it fits depends on whether Git files remain authoritative or become an export. Avoid two independently writable sources of truth. SQLite alone would not coordinate independent machines or make external launches transactional.

Measure the cost of the next change. Does a representative feature touch fewer unrelated places? Does each rule have one owner? Are concurrency failures handled predictably? A smaller root is useful evidence, not the outcome by itself. Hygiene need not be a prerequisite for every architectural improvement.

The six diagnostic probes ran separately and changed no application or test files. Multiplayer: three layers, one authority

Knut's design is a service that just broadcasts presence ("worker XX present"), claims on areas of the graph, and pushes ("others need to pull"). The data format is kept merge-friendly so the simple git structure still works. It is the minimal design for the ladder, and each layer has one job:

  • Claims are leases that expire unless renewed, so a crashed worker frees its area by itself.
