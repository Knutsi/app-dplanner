Two branches, one Test step

Two lines of work, each on its own feature branch, joining at one Test step. In one repository DPlanner plans and runs this end to end, in two different shapes. Across two repositories it reads the second repository's pull requests in the first one. In this run that marked a landing done while its PR was still open.

The answer

In short

One repository: yes, with four places where a person or a workaround was needed. Two repositories: not without a person checking every PR, because every PR number is looked up in the primary repository.

Two repos, one PR lookup

In short

DPlanner resolves every step's PR number in the project's primary repository, whatever the step's workplace. Both repositories numbered their PRs from #1, so every app PR was read as lib's PR with the same number.

Each verb that touches a PR (github set, github refresh, the playbook's progress, the window's refresher) asks _step_repo. That reads repository_facts(...).code_remote, the first code row. The worktree code already knows better: agent_briefing/worktree.py's code_placement uses the step's own row. The run hit all four ways this can go wrong:

StepWhat DPlanner didWhat was true
S4 · app memberprogress read lib PR #1, wrote its title, URL and merged onto S4, then blocked: "PR #1 merged into feature/a, but that did not accept the step"app PR #1 was open, into feature/b
S5 · app memberprogress found lib PR #2 open and refused only because its head branch differedThe head check is the one thing that kept it from merging the other repository's PR
S9 · app landingfalse donegithub refresh: "1 step(s) merged and done"app PR #3 still open; lib PR #3 had just merged into main
S10 · app Test"1 PR(s) checked, 0 updated", silently, indefinitelyapp PR #4 merged; lib has no PR #4

A false done on a landing frees everything that waits on it. Here that was the final Test, which would have started against an app without its mul/div work. With a window open, the PR refresher would do the same unattended.

The same project also showed four smaller gaps:

  • The briefing tells an app step it works in Knutsi/temp-dplanner-test-lib (protocol.py:161 uses facts.code_label).
  • The coordinator's briefing merges with gh pr merge <n> from the primary checkout.
  • A branch whose members sit in both repositories is not linted. Its launch fails with "there is no origin/feature/mix … a branch deleted after it landed".
  • The canvas cannot show which repository a card belongs to.

What did work: each step's worktree opened in its own repository, and each repository's branch was cut there. The Test step in app found lib's main on its own and depended on it through a git+ssh URL. All 24 tests passed.

Nested branches

In short

Planning a branch inside a branch is free: branch put over two existing branches nests them, and the canvas and the briefings read it right. Running it fails at the first step, because only the innermost branch gets cut.

branch_plan decides the cut for the innermost open stretch only. feature/a is "fresh", so it is created from origin/feature/int. But nothing had cut feature/int, because no step of its own had run yet:

evidence/ev/probe3-nested-first-run.txt
dplanner: could not prepare the worktree …/s2-a1-add on agent/s2-a1-add: git push:
error: src refspec origin/feature/int does not match any

It failed cleanly: no claim, no status, no worktree. One git push origin main:refs/heads/feature/int and the plan ran to the end. Inner landings opened their PRs against feature/int, merging there accepted them, and Test ran on the integrated branch.

The Sunday cut

Before any of that, every first step was refused: "'A1 add' waits on work not done yet: B6 'feature/a'". A cut is a wait of zero days. spent_since(day, today) is working_days_between − ½, which is −0.5 on a Sunday, and −0.5 is less than 0. Every branch in every plan is held until Monday. --anyway gets past it.

Parallel landings

In short

When two landings target the same base, the second conflicts the moment the first merges, and DPlanner does not notice. Send Back was the right tool and the agent used it well. But the resolution skipped review, and the merged landing still needed a person's Accept.

  • The first landing agent saw it coming. Its note N6 read: "whichever feature branch lands second will conflict on calc/__init__.py and the README list of functions, and should keep the entries from both sides". Nothing reads a note as an instruction.
  • After PR #6 merged, GitHub still reported PR #5 MERGEABLE, which was stale. git merge-tree exited 1. The step sat at ready to merge.
  • playbook send-back with the conflict as the note: the landing merged origin/main into feature/b as a merge commit, kept both sides, and the conflict was gone. Same in the Integration project, into feature/int.
  • After that execute, no Codex review ran again, because a person's send-back loops to the work and nothing follows it but the person. That is consistent with the rules, but it means the one hand-merged change got the least review.
  • Into main, the merge then left the step ready for review, because no gate had passed since its last work. Merged into feature/int, the same merge accepted it. The two behave differently by design, but it surprised me.

DPlanner knows when two open landings share a base. When one merges, it could tell the other one to merge that base back in, instead of leaving it to GitHub's stale flag and a person's eye.

A stale Test worktree

In short

A worktree is made on the first run and reused unchanged. Test, started early on purpose, resumed after both landings on a main that lacked feature/b. The agent brought its branch up to date itself; DPlanner did not.

  • Started with --anyway while only feature/a had landed, the Test agent did what its brief said: it found mul and div missing, wrote nothing, and set itself blocked. That was the right behaviour.
  • It had to report that as "outcome": "denied", because the execute schema offers only done | asked | denied. The card read "The agent was denied a permission it needed. How should it go on?", with no choices.
  • When I answered after feature/b landed, the run resumed in the same worktree, still at 8738e75. The agent, not DPlanner, updated it to 66320b4. Then 6 tests passed.

Two writers, one project

In short

Parallel branches mean parallel runs in one project, and the project file is one writer at a time. A refused launch only costs a retry. A refused advance can leave a pass stuck with no sign of why.

  • Six launches at once, two per project. In each project one was refused: "changed on disk since it was opened … nothing was written; run this again". The branch cut and the worktree had already been made. Both are idempotent, so a retry worked. A coordinator launching in parallel must retry too.
  • Two progress stages in Integration ended 2 s apart. One merged its PR on GitHub, but its pass sat at Merging: no record, no card, nothing in any log, because the detached advance's output goes nowhere. playbook advance S4 by hand finished it. The likely cause is the same concurrent-write refusal, which nothing retries. Verdict: plausible, not proven.

What held up

In short

The graph model and the agents were the strong half. Every refusal I aimed at the graph either fired or was named by lint.

  • Overlap. Test linked straight to A2 and B2 is refused at launch ("it is on feature/a and feature/b, and neither is inside the other") and named by lint. The advice to "branch remove one of them" misses the two shapes that work: link after both landings, or nest both in an outer branch.
  • Partial join. Test after Land feature/a and B2 lands on feature/b without A's work. Lint says exactly that ("the branch was cut before that work, so this step's worktree will not have it"), but the launch is not refused.
  • Names. A second branch named feature/a in one project is refused.
  • Members. In one repository, progress merged every member into its feature branch and accepted it.
  • Agents. They stopped rather than inventing missing code, predicted the conflict, resolved it when sent back, and found the sibling repository without being told how.
  • Cost. About $10 of Claude turns plus nine Codex reviews, in roughly 90 minutes.

Suggested fixes

In short

Ranked by what they prevent. The first three are small and remove the failures that need a person at every step. The rest make the parallel shape safe to leave alone.

  • 1. One repo_of(step), from the step's workplace, used by github set, refresh, progress, the window's refresher, the PR chip, the briefing's "code you are working in" and the coordinator's gh … -R. This is one function replacing several readers.
  • 2. Clamp spent_since at 0, or read a cut as done once its predecessors are. Add a test dated on a Sunday.
  • 3. Cut the enclosing stretches outside-in when a nested stretch is fresh.
  • 4. Keep the detached advance's output in the run directory, and retry an advance refused by a concurrent write. Have agent run retry the same way.
  • 5. Landings that share a base: when one merges, put a card on the others ("main moved; merge it in") and re-run their gate after a send-back.
  • 6. A blocked outcome in the execute schema, so an honest stop reads as one.
  • 7. Bring a reused worktree forward (or brief it) when a prerequisite has landed since it was cut.
  • 8. Lint a stretch whose members span repositories, and scope branch-name uniqueness per repository.
  • 9. Better overlap advice: "link Test after both landings, or put both branches on one outer branch".
