Can a playbook run headless without ever getting stuck?

Yes, as long as DPlanner never waits on a process. A question, a plan approval or a usage limit parks the run and records why. An answer, a reset or Retry now resumes the same session. Each claim below was observed in eleven small experiments.

The answer

In short

All three CLIs can be asked through one door, a dplanner ask command. Each stops cleanly when it asks and finishes the task once resumed with the answer. None of them hangs on a permission. Instead, each fails quietly and still exits 0. So the hard part is reading how a run ended, not keeping it alive.

Questions

Viable through dplanner ask and resume, for Claude, Codex and opencode. Claude's own question tool is only available when DPlanner hosts the process.

Plan mode

Viable as plan, park, then resume in an executing mode. Claude returns the plan as text; Codex uses a read-only stage.

Token exhaustion

Viable. The session survives a 429, both vendors publish their reset times, and a resume continues the same session.

Questions

In short

Headless Claude cannot use its own question tool. Asked to, it writes the question in prose and the run ends as a success. So DPlanner gives every agent a command to ask with. When DPlanner hosts Claude itself, the native question arrives fully structured, ready for a card.

The universal door

The briefing says: to ask a person, run the command and follow what it prints. The stub recorded the question and printed "Recorded as Q2. … End your turn now". The Claude, Codex and opencode agents each recorded a question and stopped without editing anything. Each was then resumed with "Raise ZeroDivisionError", and each implemented that answer.

what Codex ran, verbatim
dplanner-ask "How should divide(a, b) behave when b is zero?" \
  --choice "Raise ZeroDivisionError" --choice "Return None"

The warm path: DPlanner hosts Claude

Driven over --input-format stream-json with --permission-prompt-tool stdio, Claude offers AskUserQuestion again. The question reaches the host as a control request:

control_request · can_use_tool · AskUserQuestion
{"questions":[{"question":"Should the add() function also accept strings?",
  "header":"add() string support",
  "options":[{"label":"Yes","description":"add() should be able to concatenate strings…"},
             {"label":"No","description":"add() should only work with numbers"}],
  "multiSelect":false}]}

The host allows it with updatedInput.answers, and the agent carries on in the same turn. This is the best experience while someone is at the window, but it keeps a process alive. So a host waits only briefly. Then it parks the run, and the answer arrives later as a resume.

Plan mode

In short

Plan, park, approve, resume. Claude's plan comes back as the final text. A resume in acceptEdits or auto with "Plan approved" carries it out. Codex has no plan mode in exec, so its plan stage is a read-only sandbox.

  • claude -p --permission-mode plan: the agent explored, wrote a plan file, and tried ExitPlanMode. That failed with "disabled for this session". It then returned the plan as its result, exit 0.
  • The plan file went into ~/.claude/plans/, the user's global folder, even headless. DPlanner should keep its own copy in the run directory and leave that folder alone.
  • The resume implemented exactly the plan. With only acceptEdits, it reported "Waiting for approval to run the verification test", a denied Bash call. An approved plan needs an executing mode that can run the tests.

Never stuck

In short

In headless modes nothing waits for input. Every risk is a quiet ending: a denial or an auto-reject, reported as success. The one mode that does block is claude --bg, an interactive session in the background. From the earlier probes: no CLI times out a hung API, so a stall detector is still needed.

claude --bg made its own worktree, then waited at "This command requires approval · Do you want to proceed?" until it was stopped. It suits a person who attaches to watch a run, not unattended work.

Limits and retry

In short

Both vendors say how full the account is and when it resets, so DPlanner can stop launching before a run dies. When a run does hit the wall, its session is already saved and can be resumed after the reset. The 10-04 run did exactly that by hand.

Claude · every stream-json run
{"type":"rate_limit_event","rate_limit_info":{"status":"allowed","rateLimitType":"five_hour",

Codex · the real limit, 2026-10-04 (later resumed in the same session)
"error":{"message":"You’ve hit your usage limit. … try again at Oct 5th, 2026 2:22 AM.",
         "codex_error_info":"usage_limit_exceeded"}

Forced through a fake API with the unified headers and x-should-retry: false, Claude ended in 1 s with is_error:true and api_error_status:429. Its session transcript was already on disk. Without that header, the earlier probes saw Claude retry a 429 for about 4½ minutes.

Status checks

In short

"Installed" is not "usable". On this machine, two of the five agent CLIs on PATH could not have run a stage. A playbook's check therefore asks three questions of every role's agent: is it on PATH, which version is it, and is it signed in?

The design it implies

In short

A run is a session id plus a ledger of turns. The supervisor runs one turn, reads how it ended, and then advances the playbook, parks the run or retries it. People and coordinators act on parked runs from the Control Centre or the CLI.

flowchart LR
  L["launch stage<br/>(headless turn)"] --> E{"how did it end?"}
  E -- done --> N["next stage"]
  E -- asked / plan --> Q["question card"]
  E -- denied --> P["permission card"]
  E -- limit --> H["hold until reset"]
  E -- hang / crash --> R["retry with backoff"]
  Q -- "answer (person or coordinator)" --> RS["resume same session"]
  P -- allow / redirect --> RS
  H -- "reset or Retry now" --> RS
  R --> L
  RS --> E
  • dplanner ask is the one door. Native asks feed the same record through adapters: the host's can_use_tool calls, Claude's plan text, and denials.
  • A coordinator answers or escalates through the same verbs (questions, answer, escalate), so a human card and an agent decision share one record.
  • Execute flags per harness: Claude -p --permission-mode auto --strict-mcp-config; Codex exec --approve-for-me --add-dir <plan repo>; opencode run --auto.
  • Before each launch: check that the agent is signed in, and check the account's last known use against a threshold.

Not tested

In short

These four go into the project as explicit checks, not assumptions.

  • The wording of a real Claude subscription limit (only faked here; resetsAt is real).
  • Codex app-server approvals, the warm path for Codex.
  • Claude hooks mirroring a question from an interactive terminal run into the inbox.
  • Hours-long runs: compaction, resuming a cold session, stall thresholds on real test suites.
